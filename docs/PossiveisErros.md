Analisei o Prompt_Auth_Nativa_Hardening_v1.md cruzando com a Arquitetura Técnica e o Levantamento de Requisitos. O prompt está muito bom — cobre o essencial de auth nativa (Argon2id, rotação com detecção de reuso, lockout, RBAC) e o hardening base. Mas há lacunas que, do jeito que estão, vão gerar bugs sutis em produção (alguns já latentes no próprio doc de arquitetura). Organizei por severidade, com o "porquê" e a alternativa recomendada em cada ponto.

🔴 Crítico — corrigir junto com a migração (senão quebra em produção)
1. TIMESTAMP sem timezone quebra o LWW do sync. O doc de arquitetura define TIMESTAMP DEFAULT now() em todas as tabelas. Isso é um bug latente: now() retorna timestamptz, mas armazenado numa coluna TIMESTAMP WITHOUT TIME ZONE o offset é descartado e a comparação passa a depender do fuso do container. Como toda a estratégia de conflito é "último updated_at vence" comparando timestamps entre mobile (offline, fuso local) e servidor, isso corrompe o LWW silenciosamente.
→ Padronizar TIMESTAMPTZ em todas as colunas de data (created_at, updated_at, deleted_at, expires_at, revoked_at, locked_until, datas do financeiro). Definir na migration e forçar TimeZone=UTC na conexão. Isso precisa entrar na migration baseline da Fase 0.1.
2. Falta trust proxy — atrás do NPM, três coisas quebram ao mesmo tempo. O backend fica atrás do Nginx Proxy Manager, que termina o TLS. Sem configurar confiança no proxy: (a) req.secure é false e qualquer lógica de cookie Secure/redirect fica errada; (b) o rate-limit por IP e o lockout enxergam o IP do proxy para todos os usuários — ou seja, ou bloqueia todo mundo junto, ou não protege ninguém; (c) a coluna de auditoria ip INET em refresh_tokens registra o IP do proxy, virando inútil.
→ No main.ts: app.set('trust proxy', 1) (Express subjacente do Nest) e garantir que o NPM encaminha X-Forwarded-For e X-Forwarded-Proto. Sem isso, metade das defesas da Fase 1.5 não funciona de verdade.
3. A rotação de refresh token vai deslogar usuários aleatoriamente sob concorrência. A detecção de reuso ("token revogado apresentado de novo → mata a família") é excelente como segurança, mas é uma armadilha sob concorrência normal: duas requisições paralelas dão 401 quase juntas, disparam dois refresh simultâneos; o segundo apresenta um token que o primeiro acabou de rotacionar → o servidor interpreta como roubo e revoga a família inteira → logout falso. O mutex no frontend (que o prompt já prevê) resolve a SPA numa aba, mas não cobre múltiplas abas nem garante robustez do servidor.
→ Duas defesas no servidor, ambas: (a) SELECT ... FOR UPDATE na linha do token dentro da transação de rotação (serializa); (b) janela de graça — se o token apresentado é exatamente o replaced_by anterior dentro de ~10s, retornar o par já emitido em vez de matar a família. Só considerar reuso real fora dessa janela. Isso precisa estar explícito no prompt, senão o comportamento em prod fica flaky.
4. Duas fontes de verdade para updated_at. A arquitetura usa trigger no Postgres para updated_at; o TypeORM, por padrão, também gerencia via @UpdateDateColumn (relógio da aplicação). Ter os dois significa que ora o timestamp vem do relógio do banco, ora do relógio do app — e qualquer skew entre eles corrompe o LWW de novo.
→ Escolher uma fonte só: o trigger do banco (relógio único, autoritativo). Configurar o TypeORM para não escrever updated_at (não usar @UpdateDateColumn, ou mapear a coluna como update: false). Documentar essa decisão no doc.md.
5. Cálculo monetário com number do JS. A Fase 2.2 acerta ao recalcular no servidor e usar NUMERIC(12,2), mas NUMERIC protege só o armazenamento. Fazer valor_pedido * (percentual/100), descontos e o rateio 50/50 de comissão com number (float64) acumula erro de arredondamento — e aqui é dinheiro e comissão de terceiros.
→ Toda aritmética monetária do servidor em centavos inteiros ou com decimal.js, arredondando explicitamente (banker's rounding ou half-up, mas definido). Vale para totais de item, totais do pedido, comissão e o split de parceiros.
6. Access token continua válido após logout / desativação. O logout revoga a família do refresh (ótimo), mas o access JWT (stateless, TTL 15min) segue válido por até 15 minutos. Mesmo problema ao desativar um usuário (is_active=false) ou trocar seu role: o token vigente ignora a mudança por 15min. Para um sistema comercial com dados financeiros, isso é uma janela relevante.
→ Solução definitiva sem refatoração futura: adicionar session_epoch (ou token_version) em usuarios, embutir no JWT, e o JwtAuthGuard compara com o valor atual (cacheado por poucos segundos p/ evitar hit no banco a cada request). Logout-all, troca de senha e desativação incrementam o epoch → invalidação instantânea de todos os tokens daquele usuário. Se optar por aceitar os 15min por simplicidade agora, tudo bem — mas documente a decisão e no mínimo revalide is_active/deleted_at no guard.
7. "Deploy roda migrations" está subespecificado — e é perigoso se um dia subir 2 réplicas. Rodar migration:run dentro do startup do container app é aceitável com 1 container, mas racy assim que houver réplicas (duas rodam a mesma migration juntas).
→ Definir já como passo dedicado one-shot antes do up -d: docker compose run --rm renowa-api npm run migration:run, ou entrypoint com advisory lock do Postgres. Estrutura para crescer sem refatorar.
8. Índices de foreign keys ausentes. A arquitetura cria índices em uuid/updated_at/deleted_at, mas o Postgres não indexa FKs automaticamente. Sem índices em cliente_id, fornecedor_id, vendedor_id, itens_pedido.pedido_id, refresh_tokens.user_id/family_id, os joins e as agregações do financeiro (vendas por empresa/mês, comissões) degradam com o volume.
→ Adicionar índices em todas as FKs na migration baseline.

🟡 Importante — o prompt não cobre e deveria
9. CSRF e o efeito colateral do SameSite=Strict. A Opção A (mesma origem + Strict) mitiga CSRF, mas Strict tem um efeito indesejado: o cookie não é enviado na primeira navegação top-level vindo de fora (ex.: usuário clica num link e cai na app aparentando estar deslogado). Para um app interno pode ser tolerável, mas o comportamento surpreende.
→ Considerar SameSite=Lax no cookie de access (mantendo Strict no refresh, que só trafega em /api/auth) e, como defesa em profundidade, um CSRF token double-submit nas rotas mutantes. Decisão consciente, não default silencioso.
10. Sem tabela de auditoria. refresh_tokens registra sessões, mas não há trilha de eventos de segurança/negócio: login ok/falho, logout, troca de senha, e principalmente ações admin (criar/desativar usuário, mudar role, resetar senha). Num sistema comercial isso é accountability básica.
→ Tabela audit_log (id, user_id, action, target_type, target_id, metadata JSONB, ip, created_at), alimentada nesses pontos.
11. Graceful shutdown + config de pool. Não há menção a app.enableShutdownHooks() nem à configuração explícita do pool do TypeORM (extra: { max, connectionTimeoutMillis, idleTimeoutMillis }). No deploy (--force-recreate) requisições em voo são cortadas e conexões podem vazar. O próprio princípio 5 (Memory Safe) e o 2 (Escalabilidade) da sua skill pedem isso.
→ Habilitar shutdown hooks e fixar tamanho de pool (ex.: max: 20, timeouts explícitos).
12. Health check causa loop de restart. /health testando o banco é bom, mas se o healthcheck do Docker aponta para uma rota que falha quando o banco cai, o Docker reinicia o container em loop — e reiniciar a API não conserta o banco.
→ Separar liveness (/health/live, só o processo) da readiness (/health/ready, checa o banco). O healthcheck do compose aponta para liveness. Usar @nestjs/terminus para isso (padrão do ecossistema Nest).
13. Headers de segurança do frontend. helmet cobre só a API. A SPA servida pelo container WEB (nginx/serve na 3080) precisa dos seus próprios headers: HSTS, CSP, X-Content-Type-Options, Referrer-Policy. Hoje não há nada disso previsto.
→ Configurar no nginx do WEB (ou no NPM).
14. Política de senha e reset self-service. Não há requisito mínimo de senha (comprimento, checagem contra senhas comuns) nem fluxo "esqueci a senha". Como as contas são criadas por admin e há reset por admin, dá pra viver sem o self-service agora — mas decida conscientemente e imponha ao menos comprimento mínimo + rejeição de senhas triviais no class-validator.
15. Rate limit não escala horizontalmente. O @nestjs/throttler default usa memória local — reseta no restart e vira "por instância" se subir réplicas. O lockout no banco (failed_login_attempts) é a defesa real e está correto; só registre que, ao escalar, o throttler precisa de store compartilhado (Redis).

🔵 Questionando decisões da arquitetura (caminho melhor)
16. PDF do orçamento no cliente vs. no servidor. A arquitetura coloca @react-pdf/renderer no frontend. Problema: (a) o mobile (Fase 6) vai precisar do mesmo PDF e não reaproveita render de browser; (b) preços mudam com o tempo, e um orçamento reimpresso precisa refletir os preços da data de emissão — se o PDF é regenerado on-the-fly, ele "muda sozinho". Você já mitiga parte disso guardando preco_unitario snapshot em itens_pedido (bom), mas a geração continua não-determinística e não-arquivável.
→ Avaliar geração server-side (um PdfModule no NestJS) que gera uma vez na emissão e persiste o PDF (object storage ou coluna) vinculado ao pedido. Web e mobile baixam o mesmo artefato. Trata o PDF como o "mini-projeto" que o próprio doc pede, e resolve reimpressão/auditoria de uma vez.
17. LWW para edição interativa é perda silenciosa de dados. LWW é a estratégia correta para o sync offline do mobile. Mas para dois usuários editando o mesmo pedido/lançamento financeiro no web ao mesmo tempo, LWW = o último salvar apaga o trabalho do outro sem aviso.
→ Adicionar optimistic locking (@VersionColumn do TypeORM) nas entidades de edição interativa (pedidos, itens, financeiro). Se a versão divergiu, retornar 409 e avisar "este registro foi alterado por outro usuário". Convive bem com o LWW do sync (que continua para o mobile).
18. Assinatura do JWT. HS256 com JWT_SECRET único está ok para o cenário atual (só o backend valida). Não troque para RS256/EdDSA agora — seria complexidade sem ganho, já que o mobile vai mandar o token para a API validar, não validar localmente. Só registre uma estratégia mínima de rotação de segredo (env versionada) no doc.md.

⚙️ Transversais que faltam
19. Testes da máquina de estados de auth. O prompt não menciona testes. A lógica de rotação + detecção de reuso é a parte mais crítica e mais fácil de quebrar sutilmente (ver ponto 3). "Melhorias críticas não devem ser postergadas" se aplica aqui.
→ No mínimo testes e2e cobrindo: login → refresh → refresh (rotação ok); apresentar token antigo → família revogada; refresh concorrente → não desloga; logout → refresh subsequente = 401; vendedor em rota admin = 403.
20. Validadores de domínio. DTOs com class-validator estão previstos, mas não os validadores de CNPJ (dígito verificador) e CEP. Um CNPJ inválido entrando no cadastro contamina cliente, pedido e o financeiro depois.
→ Custom validators de CNPJ e CEP nos DTOs de cliente/transportadora.
21. Escopo de autorização no /api/sync. Como o JwtAuthGuard é global, o sync fica autenticado — bom. Mas falta definir a regra de negócio: um vendedor pode sobrescrever, via sync, dados de qualquer cliente/pedido, inclusive de outro vendedor? Precisa decidir se o sync filtra por dono/role antes de aplicar o upsert.
22. deleted_at global filter. Com soft delete em tudo, toda query precisa filtrar deleted_at IS NULL — e o endpoint de sync precisa incluir os deletados de propósito. Garanta @DeleteDateColumn nas entidades (o TypeORM aplica o filtro sozinho) e que o sync use query explícita que ignore esse filtro. Fácil de esquecer numa query raw.
23. CI mínima. Você faz build manual por serviço. Um GitHub Actions simples (lint + test + build) evita subir código quebrado — especialmente relevante agora que auth entra em jogo. Não é bloqueante, mas encaixa no "estruturar para crescer".

Resumindo a prioridade de execução: os pontos 1–8 entram no mesmo PR da migração (são correção de integridade/segurança, não melhoria opcional); 9–15 eu incluiria na Fase 0/1 ainda; 16–18 são decisões de arquitetura para você bater o martelo antes de avançar; e 19–23 distribuídos nas fases seguintes, com os testes de auth (19) idealmente junto da Fase 1.
